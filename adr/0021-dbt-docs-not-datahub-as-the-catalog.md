# ADR 0021: dbt docs is the catalog, not DataHub

**Status**: Accepted

**Date**: 2026-08-18

## Context

[ADR 0019](0019-datahub-joins-the-shared-vm.md) decided where DataHub would run
and how it would be fed. It did not ask whether DataHub was the right tool for
the catalog at all — that had been assumed since the roadmap, and every ADR
since had reasoned inside the assumption.

Asking it now produces a different answer, for three reasons that were visible
at the time and were not weighed.

- **The catalog has no consumers yet.** DataHub's value is a function of how
  many people ask it questions. Today that number is zero: one Owner, who wrote
  the models and does not need a search index to find them. The catalog exists
  to answer a question the steering committee has not yet asked. Building the
  answer before the question is what [ADR 0007](0007-python-scripts-not-airbyte.md)
  already learned about Airbyte, in the same shape.
- **Its cost is front-loaded and its value is deferred.** DataHub is a metadata
  store, a search index and several services, all of which have to be installed,
  memory-limited, patched, backed up and re-explained before they answer
  anything. ADR 0019 accepted that cost on the strength of a payoff that has no
  date attached to it.
- **The platform already produces the catalog as a by-product.** `dbt docs
  generate` emits a self-contained static site: every table, every column
  description, the compiled SQL, the tests, and a lineage graph *derived from
  `ref()`* rather than declared. DataHub's dbt source ingests exactly these two
  artifacts and then re-presents them. For a single-project, single-engine
  platform at Level 1, the second presentation adds search and a glossary UI and
  nothing else.

The reversal is cheap because DataHub was decided and never built. There is no
Terraform module, no compose service, no pinned dependency and no CI step for it
in any repository; the shared VM that would host it is a commented-out block in
`shared/main.tf`. What exists is one Dagster asset that runs `dbt docs generate`
and publishes the artifacts to the `metadata` container — which a dbt-docs
catalog needs unchanged.

**What ADR 0019 got right survives this decision.** A catalog is group-wide by
definition; a business glossary is the worst thing in the platform to duplicate;
and a continuously running catalog UI on an entity VM is what would stop that VM
from sleeping. None of that is retracted. Only the tool changes — and removing
the catalog service from the entity VM entirely serves ADR 0019's own goals
better than moving it did.

## Options considered

1. **Keep DataHub, as decided in ADR 0019** — a real catalog with search, a
   glossary UI and cross-entity lineage, at the cost of the heaviest component
   in the stack, a shared VM sized for it, and an installation nobody is waiting
   for.
2. **dbt docs as the catalog** — already generated by the pipeline, no service
   to run, no sizing, no patching. Loses search, the glossary UI, and lineage
   across entities. Makes `description:` in dbt YAML the product rather than a
   nicety.
3. **A managed catalog (Microsoft Purview or equivalent)** — removes the
   operational burden but adds per-asset billing, an Azure-specific dependency
   and a scanning configuration, to serve the same zero consumers. Level 2
   material at the earliest; see [ADR 0014](0014-duckdb-scale-ceiling.md) for how
   Level boundaries are decided.

## Decision

Option 2. dbt docs is the catalog, DataHub is removed from the platform, and
ADR 0019 is superseded.

Four things follow from choosing a tool that only reports what the YAML says,
and they are part of this decision rather than consequences of it:

**Descriptions become load-bearing, so the CI enforces them.** DataHub at least
had a UI that made an undocumented column visible as a gap. A dbt docs site with
empty descriptions is worse than no catalog, because it looks complete. The
entity CI therefore fails on a model or column without a `description`, as a
gate and not as a warning — the standard set by
[ADR 0012](0012-oidc-run-command-deployment.md)'s CI, where a check that does not
fail is not a check.

**The glossary moves into dbt YAML.** Business definitions live in the
`description` of the `mart_` model that implements them, next to the SQL that
computes them, rather than in a separate glossary file that can drift from it.
This is [ADR 0015](0015-metrics-in-marts-not-metricflow.md) applied to prose: one
definition, in one place, in Git.

**The site is generated in CI, credential-free, with `--empty-catalog`.** That
flag skips the warehouse query that populates column data types and keeps
everything else — descriptions, lineage, tests, exposures. It lets the catalog be
built by the entity CI, which by design holds no Azure credential, instead of
depending on a VM being awake. Column data types are the only loss, and nobody
consults a catalog to learn that a column is a `VARCHAR`.

**The site is a CI artifact, not a hosted service.** Every run attaches the
generated site to the workflow run; it is read by downloading that artifact, or
locally with `dbt docs serve`. Nothing is hosted, so there is no port, no
container, no NSG rule and no machine — the entity VM's only ingress stays SSH
(`modules/entity/network/main.tf`).

Publishing it to GitHub Pages is rejected deliberately: a catalog is a list of
every table and column name in the SAP extract, and a Pages site is public unless
the organisation is on GitHub Enterprise Cloud. Paying for access-controlled
hosting to serve a static site to its own author would repeat the mistake this ADR
corrects.

Serving it permanently — behind the SSH tunnel next to Dagster, or anywhere else —
is deliberately **not** decided here. It is a small change to make when a second
person needs the catalog often enough to be annoyed by downloading it. Deciding it
now, before that person exists, would be this ADR's own criticism of DataHub
applied to its replacement.

Lineage to the dashboard is handled by
[ADR 0022](0022-business-logic-in-dbt-metabase-is-presentation.md), which the
loss of DataHub makes necessary rather than optional.

## Consequences

- **Nothing has to be uninstalled.** The change is prose in five repositories,
  one Dagster docstring, and a CI job that did not exist. The `metadata`
  container keeps its purpose — durable storage for the dbt artifacts — and the
  publication asset keeps its job with a new justification.
- **The shared BI VM no longer has to be sized for a catalog.** ADR 0019 required
  it to be sized for "DataHub's documented requirements **plus** Metabase, not
  their average", with explicit container memory limits. Both requirements
  disappear. The machine is now sized for Metabase alone, and the shutdown
  reasoning in [ADR 0018](0018-scheduled-start-stop-for-entity-vms.md) is
  unaffected because the catalog does not run continuously anywhere.
- **The `os_disk_size_gb` arithmetic loses a term.** `modules/entity/compute/variables.tf`
  justifies its floor partly by "a catalogue or BI stack adds several GB of
  images plus its volumes" — the constraint that the v2.3.0 incident in
  `terraform-azure-data-platform` showed to be binding on the first entity, disk
  rather than RAM. The per-image-tag term remains; the catalogue term does not.
- **Cross-entity lineage is given up, and this is the real cost.** ADR 0019
  called it "the thing that makes the answer credible to a steering committee".
  Per-entity dbt docs sites cannot show a figure travelling across entities.
  Stated plainly: at one entity there is nothing to cross, so the loss is
  currently theoretical — and it becomes real at the second entity, which is the
  tripwire below rather than a problem being waved away.
- **Search is given up.** Finding a table means browsing a DAG or grepping the
  repository. Tolerable at tens of models by their author; not at hundreds by
  someone who did not write them.
- **Documentation stops being optional, and the CI will block work because of
  it.** This is the intended effect and it will be felt as friction the first
  few times. The alternative is a catalog that lies by omission.
- **The catalog is only as fresh as the last CI run**, and reading it takes a
  deliberate step — downloading an artifact rather than opening a bookmark. Both
  are narrower than DataHub would have been, and both match the current audience
  exactly. The second is also the signal to watch: the day downloading it becomes
  annoying is the day it is worth hosting.
- Revisited if any of these becomes true: a second entity is onboarded and a
  question genuinely spans both; someone other than the Owner needs to find a
  table they did not create; or the model count passes the point where browsing
  a DAG replaces searching. Two of the three at once is the signal to reopen, and
  the answer then is option 3 rather than a return to self-hosted DataHub —
  running a metadata platform was never the part that created value.
